# ベンチマーク

最初の節は、0.20のRust版とTypeScript版の、sasacode自身にかかる時間とメモリの比べ。次の節（2026-11-18）が、Rust版でモデルに課題を解かせた最初の記録。それより後の節は、どれもTypeScript版（0.15まで）を測ったもの。課題はこのリポジトリのTypeScript版の複製を相手にしていて、Rust版の計測でも、TypeScript版のころのmain（5c5e748）を複製して使った。そのため、課題の中のファイルのパスやコマンド（`bun`など）は当時のもの。`bench/`はリポジトリに含めない手元の道具で、0.20の書き換えでも変えていない（`rust/DECISIONS.md`のADR-009）。2026-11-18に、設定を足す`--config`と、project-checksの`verifyOnFinish`を課題ごとに設定する`--verify`を足した。

手元のベンチマークスクリプト（`bench/`、リポジトリには含めない）は、実際のコーディング作業をこのリポジトリの複製に対して実行し、トークン数・キャッシュのヒット率・速度・成否を記録する。LLM以外の条件を揃えて比べられるよう、ヘッドレスのCLI（`--output jsonl`）を通して測る。

```bash
bun bench/run.ts --model <provider/model> --budget 1000000 --bin ~/.local/bin/sasacode --env ~/.sasacode/.env --context 1000000 \
  [--tasks fix-edit-count,feature-read-tail] [--passes 1] [--max-turns 60]
bun bench/summarize.ts bench/results/<結果>.jsonl
```

- タスクごとに`git clone`した作業ディレクトリを新しく作り、`bun install`してから実行する。権限は`auto`（使い捨てのディレクトリの中だけ）。
- `--context`でモデルのコンテキスト長を伝える（既定の128kのままだと、途中で圧縮が入る）。
- `--config <JSONファイル>`は、計測用の設定（`config.json`）に中身を足す（`providers.ollama.baseUrl`など）。`--verify`は、project-checksを有効にし、課題の採点のコマンドを`checks.test`に、`verifyOnFinish`を`["test"]`にする。
- 予算は上限として扱い、使い切った時点でタスクの途中でも打ち切る（v0.6.3の記録のころはタスクの合間でしか確かめず、1Mの予算で3.1Mを使った）。
- タスクごとに「テストが通ったか」（`ok`）と「自分で作業を終えたか」（`autonomous`：どのプロンプトも上限や打ち切りでなく終わった）を分けて記録する。loop-guardの注意と拒否の回数も数える。2026-11-06からは、tool-repairの修復（直した内容も）、本文から拾った呼び出し、`Unknown tool`と引数エラー、repetition-guardの停止、editのゆるい一致、圧縮の回数も数え、イベントの生ログを結果の横（`<結果>.raw/`）に残す。

## Rust版とTypeScript版：sasacode自身にかかる時間とメモリ（2026-11-18、v0.20.0）

0.20でRustに書き換えた効果を、同じ作業を両方の版にさせて比べた。モデルには、すぐに応答を返す偽のサーバー（`sasacode-fake-model`）を使った。そのため、ここの数字はsasacode自身にかかる分だけで、モデルを待つ時間は入っていない。本物のモデルは1回の応答に数秒かかるので、会話全体にかかる時間はほとんど変わらない。変わるのは、起動の速さと、CPUとメモリの軽さになる。

- TypeScript版：TypeScriptを消す前のmainの最後（1f95bbf、`--version`は0.15.2）。リリースと同じ`bun build --compile --minify`で作った（bun 1.4.4）
- Rust版：834bddc（0.20.0、未リリース）。リリースと同じ`cargo build --release`で作った（Homebrewのrustc 1.98.1）
- Apple M1 Pro（10コア、32GB）、macOS 26.6.2。電源につなぎ、低電力モードはオフ。ほかのアプリがCPUを3コア分ほど使っていた
- 両方の版を交互に動かし、中央値をとった。回数は、起動と`-p`が各15回、再開が各10回、TUIが各8回。最初の1〜2回は捨てた
- どの回も、終了コードと、偽のサーバーが受けた問い合わせの数を確かめた。ツールの結果も確かめた（`read`が最後の行まで返した、`bash`が`echo`の出力を返した、`edit`が20か所を変えた）。両方の版が同じ作業をしている
- 自動の更新確認は、両方とも設定（`updateCheck: false`）で止めた
- 時間は、sasacodeのプロセスだけを単調な時計で測った（偽のサーバーの起動は含まない）。CPU時間（userとsysの和）と最大メモリは、`wait4`でそのプロセスについて取った
- 道具は手元の`bench/overhead/`（リポジトリには含めない）。偽のサーバーは`cargo build --release -p sasacode-testing --bin sasacode-fake-model`で作る

## Rust版：Gemma4 e2bの基準と、editのヒントと終える前の確認（2026-11-18、sasacode v0.20.0）

Rust版（#159）でモデルに課題を解かせた最初の計測。まず、v0.15.2の記録（次の節）と同じ2課題を2回ずつ測り、Rust版の基準にした。次に、editの失敗に見るべき行を添える変更（B）と、project-checksの`verifyOnFinish`（A）を入れたブランチで、同じ2課題を2回ずつ測り直した。Bだけの1回と、DeepSeek V4.1 Flashでの前後（M0とfix-edit-count、1回ずつ）も測った。

- 基準はmainのa4f1d43（#159と#163の後）、変更後は`feat/edit-hints-verify-on-finish`。どちらも`cargo build --release`で作った
- Ollama 0.32.13（ポート11436）、`gemma4:e2b`（Q4_K_M）、Apple M1 Pro 32GB。v0.15.2の記録はOllama 0.40.15で、版が違う。0.32.13はキャッシュの読み込みを報告しないので、キャッシュのヒット率は0%と出る。出力速度も、前回の42〜46トークン/秒に対して、複数のリクエストを送った回では8〜13トークン/秒で、前回の表とは比べられない
- コンテキストは32,768、推論の深さは既定の`high`、権限は`auto`、ターン上限は30
- 変更後の計測には`--verify`を付けた。採点のコマンド（`bun test packages/tools`など）が`checks.test`になり、`verifyOnFinish`は`["test"]`になる。「Bだけ」は同じビルドで`--verify`を付けずに測った
- 電源の状態は`pmset -g batt`で各回の前後に確かめた。基準の4回は、電源につないだままで100%から減らなかった。変更後の1回目は、始める前の読みが「100%、放電中」だった（電源の行は取っていない）。そのまま始め、fix-edit-countに23分かかるあいだに95%まで減り、終わったときは充電中だった。その後の回は電源につないだままで、100%に戻った

- editのヒント（B）は、どの回でも出なかった。`old_string`が見つからないeditも、複数に一致するeditも起きなかったため。editの失敗は、基準2回目の字下げの不一致と、変更後1回目のないファイルへのeditだけで、どちらもBの対象ではない。Bの効き目は、この計測ではわからない。
- 各2回（Bだけは1回）の計測なので、成否にはばらつきが大きく含まれる。

### DeepSeek V4.1 Flash：前後の比較（M0とfix-edit-count、各1回）

終える前の確認で、大きいモデルの作業が遅くなったり、余計な注意が出たりしないかを見た。`docs/milestones.md`のM0（`mean()`のoff-by-oneで`bun test`が落ちる小さなプロジェクトを、ヘッドレスで直す）を、同じ指示（「bun testが失敗しています。原因を調べて直してください。」）で、基準と変更後に1回ずつ実行した。M0の題材はリポジトリに残っていないので、同じ形のもの（`src/stats.ts`の`mean()`と、テスト3つ）を作り直した。変更後は`checks.test`を、`bun test`の前後に時刻をファイルへ書き足すスクリプトにして、確認が流れたかを記録した。あわせて、ベンチマークのfix-edit-countも1回ずつ実行した（予算300,000、コンテキスト1,000,000、ターン上限60）。

- M0の変更後では、モデルが`edit`で直してテストを流し、終わりの報告を書いた後に、確認の検査が1回だけ流れて通った（0.06秒）。何も返さず、そのまま終わった。M0の時間は、どちらもstdinを5秒待った分を含む（実行のときにstdinを閉じていなかったため）。
- fix-edit-countの変更後も、確認は何も返さなかった。モデルは`edit.ts`を直した後、自分でテストを流して通してから終えた。こちらは検査の実行を記録していない（イベントには出ない）。
- fix-edit-countの時間の差は、モデル以外の部分（ツールの実行）の差だった。基準では、モデルが最後にリポジトリ全体のテスト（`bun test`）も流していて、その分が長い。どちらの課題も1回ずつなので、確認による遅れは、ばらつきに埋もれて見えない。
- この前に、修正前のビルドでfix-edit-countの変更後を1回測った（成功・自力完了、12リクエスト、210,239トークン、286秒。確認0回）。時間が長いのは、モデルがリポジトリ全体のテストを2回とe2eのテストを流したため。このときの記録から、`bun test packages/tools 2>&1 | tail -30`のようにパイプを通したbashの成功を、検査が通ったと数えていたことに気づいた。パイプの終了コードは`tail`のもので、テストが落ちても成功になる。そこで、bashは落ちたときだけを数えるように直し（81e863c）、上の表はその後のビルドで測った。Gemma4の変更後の2回とBだけは、この修正の前のビルドで測った。変更後の4つの実行では、bashで検査のコマンドが通った場面はなかったので、結果は変わらない。
- fix-edit-countの`bench/run.ts`は、リポジトリの外のディレクトリから実行した。Bunは実行したディレクトリの`.env`を読むので、手元のcheckoutの`.env`にある古い`CMD_API_KEY`が使われ、401になったため。

- 1回目のfix-permission-redirectは、write-guardの見ない形でテストファイルを書き戻した。`read`の行番号の数字とタブだけを消し、桁揃えの空白5つを全行の先頭に残した（`     1\t…`が`     …`になった）。write-guardが外すのは「空白、数字、タブ」が1ずつ増える形だけなので、そのまま書き込まれた。TypeScriptは行頭の空白で壊れないので、テストの結果には響いていない。Pythonなど字下げに意味のある言語なら壊れる。この形は、0.20のRust版のwrite-guardで外すようにした（#163）。
- 4回とも、失敗の理由は作業の中身だった。

## jev-guard：セッションログの実コマンドと、接続先の比較（2026-09-26）

### わかったこと

- キャッシュはよく当たる。会話を書き換えず追記だけするので、入力の先頭部分が毎回同じになり、ターンを重ねるほどヒット率が上がる（11番目以降は98%）。キャッシュなしで処理された入力は、全体の約4%（127k）だけだった。
- トークンの大半は長いループで使われる。35ターンと60ターンの2タスクで、全体の91% を使った。1リクエストあたりの入力は、後半になると36k前後になる。60ターンの上限で止まった`/version`のタスクは、型チェックは通ったものの、途中で必要のない探索（web_fetchを含む）を繰り返していた。
- 1番目のリクエストはキャッシュされなかった（0%）。システムプロンプトの先頭近くに作業ディレクトリのパスがあり、ベンチマークではタスクごとに異なる一時ディレクトリを使ったため、共通部分がすぐに途切れた。同じプロジェクトで使う普段の状況では、別セッションでも共通部分がキャッシュされるはず。変わらない部分をシステムプロンプトの前に、環境の情報を後ろに置けば、別のプロジェクト間でもヒットするようになる（未実施）。
- ツール呼び出しの形式は崩れなかった。179回のうち失敗は1回、`tool-repair`が直す必要のある呼び出しは0回。修復が役立つのは、もっと小さいモデル。
