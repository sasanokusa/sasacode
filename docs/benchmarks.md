# ベンチマーク

手元のベンチマークスクリプト（`bench/`、リポジトリには含めない）は、実際のコーディング作業をこのリポジトリの複製に対して実行し、トークン数・キャッシュのヒット率・速度・成否を記録する。LLM 以外の条件を揃えて比べられるよう、ヘッドレスの CLI（`--output jsonl`）を通して測る。

```bash
bun bench/run.ts --model <provider/model> --budget 1000000 --bin ~/.local/bin/sasacode --env ~/.sasacode/.env --context 1000000 \
  [--tasks fix-edit-count,feature-read-tail] [--passes 1] [--max-turns 60]
bun bench/summarize.ts bench/results/<結果>.jsonl
```

- タスクごとに `git clone` した作業ディレクトリを新しく作り、`bun install` してから実行する。権限は `auto`（使い捨てのディレクトリの中だけ）。
- `--context` でモデルのコンテキスト長を伝える（既定の 128k のままだと、途中で圧縮が入る）。
- 予算は上限として扱い、使い切った時点でタスクの途中でも打ち切る（v0.6.3 の記録のころはタスクの合間でしか確かめず、1M の予算で 3.1M を使った）。
- タスクごとに「テストが通ったか」（`ok`）と「自分で作業を終えたか」（`autonomous`：どのプロンプトも上限や打ち切りでなく終わった）を分けて記録する。loop-guard の注意と拒否の回数も数える。

### わかったこと

- **キャッシュはよく効く。** 会話を書き換えず追記だけするので、入力の先頭部分が毎回同じになり、ターンを重ねるほどヒット率が上がる（11番目以降は 98%）。キャッシュなしで処理された入力は、全体の約 4%（127k）だけだった。
- **トークンの大半は長いループで使われる。** 35 ターンと 60 ターンの2タスクで、全体の 91% を使った。1リクエストあたりの入力は、後半になると 36k 前後になる。60 ターンの上限で止まった `/version` のタスクは、型チェックは通ったものの、途中で必要のない探索（web_fetch を含む）を繰り返していた。
- **1番目のリクエストはキャッシュされなかった（0%）。** システムプロンプトの先頭近くに作業ディレクトリのパスがあり、ベンチマークではタスクごとに異なる一時ディレクトリを使ったため、共通部分がすぐに途切れた。同じプロジェクトで使う普段の状況では、別セッションでも共通部分がキャッシュされるはず。変わらない部分をシステムプロンプトの前に、環境の情報を後ろに置けば、別のプロジェクト間でもヒットするようになる（未実施）。
- **ツール呼び出しは壊れなかった。** 179 回のうち失敗は1回、`tool-repair` が直す必要のある呼び出しは0回。修復が役立つのは、もっと小さいモデル。
